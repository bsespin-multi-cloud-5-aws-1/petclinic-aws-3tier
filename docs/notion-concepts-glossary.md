# 멘토링 질문을 이해하기 위한 개념 정리 (우리 시스템 예시로)

> `notion-mentoring-questions.md` 의 질문 하나하나가 무슨 말인지, 우리 구성(mc-deploy)에 대입해 풀어 쓴 원고.
> 흐름 복습: 브라우저 → Route 53 → **CloudFront**(+WAF) → Public ALB → **Apache(WEB)** → Internal ALB → **Tomcat(WAS)** → RDS Proxy → RDS.

## 1. CloudFront 캐시 키 · WAF rate-all

**Behavior(비헤이비어)** — CloudFront 에서 "이 경로 패턴의 요청은 이렇게 처리해라"는 규칙. 우리는 4개:
| Behavior(경로 패턴) | 처리 | 왜 |
|---|---|---|
| `/static/*` · `/images/*` · `/petclinic/resources/*` | **캐시함**(1일) | css·js·이미지·영상은 누가 요청해도 내용이 같다 → 엣지에 한 번 받아두고 다시 줌 |
| `/maintenance.html` | S3 에서 가져옴 | 점검 페이지 |
| `*` (나머지 전부: `/petclinic/vets`, `/owners/find`…) | **캐시 안 함**, 매번 ALB 로 | 사용자·시점마다 내용이 달라지는 JSP 응답(동적) |
- "**정적 Behavior**" = 위 첫 줄처럼 캐시하는 규칙. "**동적**" = 마지막 줄.
- "**CloudFront 가 정적을 흡수한다**" = css·이미지·영상 요청은 엣지가 캐시에서 바로 응답하므로 **ALB·Apache·Tomcat 은 그 요청을 아예 보지 않는다**는 뜻. 어제 확인: `hero.mp4` 첫 요청 `Miss`(오리진에서 가져옴) → 두 번째 `Hit`(엣지에서 응답).

**캐시 키** — CloudFront 가 "같은 파일이다/다르다"를 판단하는 기준. 우리는 **URL 경로만** 본다(쿼리 문자열·쿠키 무시). 그래서 `/static/a.css` 와 `/static/a.css?v=2` 를 **같은 것**으로 취급.

**캐시 버스팅(cache busting)** — 파일을 바꿨는데 브라우저/CDN 이 옛 파일을 계속 주는 문제를 깨는 기법. 보통 `a.css?v=2` 처럼 URL 을 바꿔 "새 파일"로 인식시킨다. 우리는 쿼리를 무시하므로 이 방법이 **안 통하고**, 대신 ① 무효화(`create-invalidation`: 엣지 캐시를 지워라) 또는 ② 경로 자체를 바꿈(`/static/v2/a.css`). 어제 Green 전환 뒤 CSS 가 옛것으로 보인 게 바로 이 문제였고 무효화로 해결.
- 질문의 뜻: "무효화(배포마다 명령 한 번, 지연 수십 초)와 경로 버전(빌드가 경로를 바꿔야 함) 중 실무에서 무엇을 쓰나?"

**rate-based rule / rate-all** — WAF 규칙 중 "**같은 IP 가 5분 안에 N 번 넘게 요청하면 차단**". 우리 규칙 이름:
- `rate-all`: 모든 경로, IP 당 5분 **2,000** 요청 초과 → 403
- `rate-booking`: `/visits/new`(예약 폼)만, IP 당 5분 **100** 초과 → 403 (예약 폭주·봇 대비)
- 질문의 뜻: 2,000·100 은 감으로 정한 숫자. 실무에선 무엇(평시 최대 RPS? p95?)을 보고 정하는지, 회사 공유 IP 오탐은 어떻게 다루는지.
- "읽기 API 에 5~10초 캐시" = `/petclinic/vets.json` 같은 조회 응답을 몇 초만 캐시하면 폭주 때 DB 부하가 크게 준다. 대신 그 몇 초 동안 새 데이터가 안 보일 수 있다(정합성) → 허용되는지 묻는 것.

## 2. WEB 계층 · 랜딩 · mod_proxy
- **랜딩(landing) 페이지** = 첫 화면 `index.html`(미션 동물병원 소개 + 영상). 지금은 **WEB EC2 의 Apache 가 파일로** 서빙.
- "**랜딩을 옮긴다**" = 그 index.html 과 css·영상을 EC2 가 아니라 **S3 버킷에 올리고 CloudFront 가 S3 에서 직접 읽게** 하는 것. 그러면 정적 파일에 서버가 필요 없다(비용↓·패치 대상↓). 대신 WEB 계층의 역할이 줄어 "3-Tier 에서 WEB 이 왜 있나"가 더 도드라진다.
- **mod_proxy(리버스 프록시)** = Apache 가 `/petclinic/…` 요청을 받아 뒤의 Internal ALB(→Tomcat)로 대신 전달하고 응답을 돌려주는 것. 사용자는 Tomcat 주소를 모른다. **mod_jk** 는 같은 일을 AJP 라는 별도 프로토콜로 하는 모듈인데, ALB 가 AJP 를 이해 못 해 우리 구조에선 못 쓴다.
- 질문의 뜻: "CloudFront 가 정적을 다 받아주면 WEB(Apache) 계층은 사실상 프록시만 한다. 그럼에도 계층을 유지하는 이유(보안 경계·헤더 제어·전통적 3-Tier 요구)를 어떻게 설명하나?"

## 3. Redis · SQS
- **세션** = 로그인 상태 같은 "이 사용자와의 대화 기억". WAS 가 2대면 1번 서버에 기억이 있고 2번엔 없다 → 공유 저장소(**Redis/ElastiCache**)에 두거나, ALB 가 같은 사용자를 같은 서버로 보냄(**스티키 세션**). PetClinic 은 로그인이 없어 기억할 게 없다 → 둘 다 불필요.
- **SQS(큐)** = 요청을 줄 세워 두고 뒤에서 천천히 처리하는 통. 예약 폭주 때 "일단 접수(큐)"하고 DB 에는 순서대로 쓰면 DB 가 안 죽는다. 단 앱이 큐에 넣고(producer) 꺼내는(consumer) 코드가 필요 → "소스 0줄" 원칙과 충돌.
- 질문의 뜻: 코드 변경을 감수할 만큼 SQS 이득이 큰가, 아니면 우리처럼 Proxy 풀링 + 증설로 버티는 게 실무적인가.

## 4. CloudWatch Agent · Golden AMI · Image Builder
- **user_data(init script)** = EC2 가 처음 켜질 때 실행되는 스크립트. 지금은 여기서 Apache/Tomcat 설치·앱 빌드·CW Agent 설치까지 다 한다(WAS 8분).
- **Golden AMI** = 설치가 끝난 상태를 통째로 이미지로 떠 둔 것. 그걸로 켜면 설치 없이 1~2분 만에 뜬다.
- **EC2 Image Builder** = AMI 를 자동으로 굽는 AWS 서비스(레시피 정의 → 매주 자동 빌드·테스트). 수동 `create-image` 는 사람이 인스턴스 하나 세팅하고 버튼 누르는 것.
- 질문의 뜻: 3주 프로젝트에서 자동화 파이프라인까지 만들 가치가 있나, 수동 AMI v1/v2 로 충분한가.

**"WAR 에 DB 정보가 빌드 시 박힌다"** — PetClinic 은 Maven 이 빌드할 때 `datasource-config.xml` 안의 `${jdbc.url}` 자리에 실제 값을 **글자로 써넣는다**(Maven 필터링). 결과물 `petclinic.war` 안에 `jdbc:mysql://mc-rds-proxy…` 와 비밀번호가 문자 그대로 들어 있다. 그래서:
- WAR 는 **그 환경 전용**(다른 계정·다른 DB 면 다시 빌드) → AMI 에 WAR 를 넣으면 AMI 도 환경 전용이 되고 비밀번호까지 들어감.
- "환경 독립적으로 만드는 표준" 세 가지:
  1. **JNDI**: Tomcat 설정 파일(`context.xml`)에 DB 접속정보를 두고, 앱은 `java:comp/env/jdbc/petclinic` 이라는 **이름**만 찾는다. WAR 는 어디서나 같고, 부팅 때 context.xml 만 쓰면 됨. PetClinic 에 이미 `javaee` 프로필로 준비돼 있어 코드 수정 없이 가능.
  2. **환경변수**: 앱이 시작할 때 `DB_URL` 같은 환경변수를 읽는다 — Spring Boot 방식이라 이 앱은 코드 수정 필요.
  3. **Parameter Store/Secrets Manager 에서 부팅 시 조회**: 지금 우리가 하는 방식(조회 → 빌드). 단 조회한 값을 WAR 에 굽는 대신 설정 파일에 쓰는 게 이상적.
- 질문의 뜻: 이 앱(옛날식 Spring XML)에서 실무자는 보통 1번(JNDI)으로 가나?

## 5. 로그 수집 범위
- 우리 5종: 앱 로그(Apache·Tomcat) · ALB 액세스 로그 · WAF 로그 · SSM 세션 로그 · CloudTrail(누가 AWS 에서 뭘 했나).
- 안 켠 것: **VPC Flow Logs**(어떤 IP 가 어떤 포트로 통신했나) · **RDS slow query log**(2초 넘게 걸린 SQL 목록) · S3 데이터 이벤트(누가 파일을 열었나).
- 질문의 뜻: 사고 조사 때 실제로 쓰이는 로그가 무엇인지 경험을 듣고, 특히 Phase 3 병목 분석에 slow query log 가 값어치가 있는지.

## 6. ASG Target Tracking · 워밍업 · 예약 증설
- **Auto Scaling Group(ASG)** = 인스턴스 수를 자동으로 늘리고 줄이는 묶음. **Target Tracking** = "이 지표를 이 값 근처로 유지해라"(온도 조절기처럼). 예: CPU 평균 60% 유지 → 넘으면 추가, 남으면 축소.
- **지표 후보** ① `ASGAverageCPUUtilization`(CPU) — 단순하지만 JVM 은 CPU 가 늦게 오른다. ② `ALBRequestCountPerTarget`(**WAS 한 대가 1분에 받는 요청 수**) — 트래픽에 바로 반응. 우리 설계값 **300/대** 는 "한 대가 1분에 300 요청 넘으면 늘려라"인데 근거 없이 정한 숫자.
- 질문의 뜻: 근거는 보통 **부하 테스트**로 "한 대가 p95 2초 이내로 버티는 최대 RPS" 를 재서 그 70~80% 로 두는데, 멘토님은 어떤 지표를 1순위로 쓰는지.
- **워밍업** = 새 인스턴스가 켜져서 실제로 요청을 받을 수 있기까지 걸리는 시간. 우리는 부팅 때 빌드까지 하므로 **8분** → "폭주 감지 → 증설 → 8분 뒤 투입"이면 이미 늦는다. Golden AMI 면 1~2분.
- **예약 증설(Scheduled scaling)** = "매일 09:45 에 4대로 늘려라"처럼 시간표로 미리 늘리는 것(영상 공개 15분 전). 질문의 뜻: 워밍업이 길면 반응형 증설 대신 예약 증설이 현실적 답인가.

## 7. Secrets Manager · 비밀 교체 · VPC 엔드포인트
- **비밀 교체(rotation)** = 비밀번호를 주기적으로 새로 바꾸는 것. RDS 가 만든 admin 비밀(`rds!db-…`)은 **7일마다 자동 교체**되고 끌 수 없다.
- 문제: WAS 는 빌드할 때의 비밀번호를 WAR 에 굽는다 → 7일 뒤 admin 비밀번호가 바뀌면 WAS 가 새 연결을 못 맺는다(9/22쯤 장애 예약). 해법으로 **앱 전용 사용자(`petclinic_app`)** 를 만들고 그 비밀은 **교체하지 않는 것**으로 뒀다(코드 `441e4a7`, 미적용).
- 질문의 뜻: "교체 없음"이 보안 관점에서 허용되는 수준인가? 교체를 하려면 (a) 교체 때마다 WAS 재빌드·재기동, (b) JNDI 로 바꿔 설정 파일만 갱신, (c) IAM 인증(비밀번호 대신 15분짜리 토큰, 코드 필요) 중 실무 표준은?
- **VPC 엔드포인트** = Secrets Manager·SSM 같은 AWS 서비스에 **인터넷(NAT)로 나가지 않고 VPC 안 사설 경로**로 가게 하는 문. 시간당 요금(AZ 당 ≈ $8/월)이 들지만 NAT 전송비가 줄고 트래픽이 VPC 를 안 벗어나 보안상 선호. 질문의 뜻: 소규모에서도 이걸 두는 게 표준인가.

## 8. 개인정보 보존·파기 · 진료 파일 S3
- 우리 개인정보 = RDS 의 `owners`(이름·주소·전화)·`pets`·`visits` **행(row)**. 파일이 아니라 DB 안 데이터.
- "**보존·파기를 증명**" = 법(개인정보 보호법)이 "보존기간이 지나면 파기하라"고 하므로, 평가/감사에서 "기간을 정했고, 지나면 지운다(또는 지웠다)"를 보여줘야 한다. DB 행은 S3 처럼 lifecycle 규칙이 없어 **정책 문서 + 주기적 삭제 작업(예약 SQL) + 삭제 로그**로 증명한다. 질문의 뜻: 프로젝트 수준에선 문서만으로 충분한가.
- "**진료 파일 S3**" = 원래 시나리오(9/14 이전)에 X-ray·진료기록 파일을 S3 에 저장하고 Object Lock(삭제 불가)·Macie(개인정보 탐지)까지 넣었다가 범위를 줄이며 뺐다. 질문의 뜻: 발표 평가에서 "의료 데이터 보호" 축이 약해졌는데 다시 넣는 게 유리한가.

## 9. 권한(ABAC · 기본 거부)
- IAM 은 허용하지 않은 건 전부 거부(암묵적 거부). 우리 역할들은 "이 비밀 하나", "이 S3 접두사"처럼 **자원 단위로만 허용**.
- **ABAC(태그 기반)** = "Project=petclinic-3tier 태그가 붙은 자원만 만질 수 있다"처럼 **태그로 권한 범위**를 정하는 방식. 자원이 늘어도 정책을 안 고친다. 단 태그를 안 붙이거나 바꿔치기하면 뚫리므로 태그 변경 권한도 막아야 한다. **SCP** = 조직 단위로 계정 전체에 거는 상위 정책(kdt5 팀 계정엔 없음).

## 10. 네이밍
- "환경·계정을 이름에 넣나" = `mc-alb-public` 처럼 짧게 갈지 `mc-lab-alb-public`(env 포함)처럼 갈지. 이름에 넣으면 한눈에 구분되지만 길이 제한(ALB 32자)에 걸리고, 태그로 두면 이름은 짧고 필터는 태그로.
- "이름 변경 불가 리소스" = ALB·대상 그룹은 만든 뒤 이름을 못 바꾼다(RDS 식별자는 변경 가능하나 엔드포인트가 바뀜). kdt5 의 `test-Public-ALB`·`Targetgroup-web` 을 규칙에 맞추려면 **지웠다 다시 만들어야** 한다 → 그럴 가치가 있나, 태그로만 정리하고 두나.

## 11. CloudFront 를 "보안 경계"로
- **WAF 범위**: CLOUDFRONT(전 세계 엣지에서 차단) vs REGIONAL(서울 ALB 앞에서 차단). CloudFront 를 빼면 WAF 를 ALB 에 직접 붙인다(REGIONAL).
- 우리가 CloudFront 를 두는 이유는 캐시보다 **경계**: 공격이 엣지에서 끊기고(Shield), ALB 주소가 숨겨지고(프리픽스+헤더), 전 계층이 죽어도 점검 페이지가 나간다.
- 질문의 뜻: 국내 사용자만·트래픽 작은 서비스에서 이 논리가 실무자에게 설득력 있는지, 아니면 "ALB + WAF REGIONAL 이 더 흔하고 단순하다"가 정답인지. **VPC origins** = CloudFront 가 프라이빗 ALB 에 직접 붙는 신기능(ALB 를 인터넷에서 완전히 숨김).

## 추가 판단들
- **Blue/Green 단위**: 지금은 **롤링**(AZ-a 교체 → 확인 → AZ-c 교체, 한 번에 한 버전만 존재). **Green TG 가중치** = 새 버전 서버 묶음(Green)을 따로 띄우고 리스너에서 10%→50%→100% 로 트래픽 비율을 옮기며, 문제 나면 0% 로 즉시 롤백. 더 안전하고 발표에 좋지만 서버 2배·설정 복잡.
- **Multi-AZ**: RDS 대기 복제본을 다른 AZ 에 항상 켜 둠(장애 시 1~2분 자동 전환, **RPO 0**). 비용 2배(≈$40→$80). 실습 3주에 켜 둘 가치 vs 발표 때만 켜기.
- **NAT 2개**: 프라이빗 서브넷이 인터넷(dnf·SSM·Secrets)으로 나가는 문. AZ 당 하나면 한 AZ 장애 때도 다른 AZ 가 살아있지만 고정비 ≈ $86/월(둘 다). 실습이면 1개로 줄이고 "운영이면 2개"로 설명해도 되나.
- **Bastion → SSM**: Bastion = 22번 포트를 연 점프 서버(키 관리·패치·공인 IP 노출). **SSM Session Manager** = 포트·키 없이 IAM 권한으로 접속하고 세션이 CloudWatch 에 기록됨. kdt5 팀은 아직 Bastion 사용 중 → 전환을 주장할 근거(22번 제거·키 유출 위험 0·감사 로그)를 어떻게 말하나.
