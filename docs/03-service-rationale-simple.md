# 우리가 쓰는 AWS 서비스, 왜 쓰나 — 3장 요약

- 1팀 Mission Critical · 2026-09-13 · 팀원 공유용 (상세판: `03-service-rationale.md`)
- 읽는 법: 한 서비스 = 한 줄. "문제 → 해결" 만 기억하면 됩니다.

---

## 슬라이드 1. 전체 그림 — 요청이 지나가는 길

```
사용자 → Route 53 → CloudFront + WAF → Public ALB → WEB(Apache) → Internal ALB → WAS(Tomcat) → RDS Proxy → RDS(MySQL)
         [진입: 앞에서 거른다]          [WEB·WAS: 부족하면 자동으로 늘린다]                  [DB: 하나뿐이니 지킨다]
```

폭주 시나리오: 유튜브 노출로 요청이 평시의 10배(초당 50 → 500~1,000).

**대응 원칙 세 줄**

1. **앞에서 거른다** — 이미지 같은 정적 파일과 이상 트래픽은 서버까지 오지 못하게 한다.
2. **부족하면 늘린다** — WEB·WAS 서버는 여러 대로 복제 가능하니 자동으로 증설한다.
3. **DB는 지킨다** — DB는 마음대로 늘릴 수 없으니 연결 수를 조절하고 예비 DB를 둔다.

---

## 슬라이드 2. 서비스별 한 줄 이유

### 진입 (앞에서 거른다)

| 서비스 | 문제 | 해결 |
|---|---|---|
| **Route 53** | 도메인이 없으면 HTTPS도, CloudFront도 못 붙임 | 도메인을 사서 CloudFront에 연결 |
| **CloudFront** | 사진·CSS 같은 정적 파일 요청이 서버 대역폭을 다 잡아먹음 | 정적 파일은 CloudFront가 캐시해서 대신 응답 → 서버에는 동적 요청만 감 |
| **WAF** | 특정 IP나 봇이 예약 API를 무한 호출 | IP당 요청 횟수 제한, 이상 요청은 서버 도달 전에 차단 |

### WEB · WAS (부족하면 늘린다)

| 서비스 | 문제 | 해결 |
|---|---|---|
| **ALB** (Public·Internal) | 서버 1대에 몰리면 죽고, 죽은 서버로 요청이 감 | 여러 서버에 분산 + 헬스체크로 죽은 서버 자동 제외 |
| **Apache·Tomcat 튜닝** | 기본 설정은 동시 접속 수가 낮음 | 서버 늘리기 전에 1대당 처리량부터 올림 (설정값 몇 줄) |
| **Auto Scaling (ASG)** | 폭주 때 사람이 서버를 손으로 못 늘림 | CPU 60% 넘으면 자동 증설, 유튜브 공개 시각에 맞춰 미리 증설 예약 |
| **SSM Session Manager** | 서버 접속하려면 Bastion 서버 + 22번 포트 + SSH 키 관리 필요 | Bastion 없이 콘솔에서 바로 접속, 포트 안 열고 접속 기록 자동 저장 |

### DB (하나뿐이니 지킨다)

| 서비스 | 문제 | 해결 |
|---|---|---|
| **RDS Proxy** | WAS가 8대로 늘면 DB 연결 수 한도 초과 → 연결 거부 | WAS와 DB 사이에서 연결을 모아서 관리, 한도 안 넘게 조절 |
| **RDS Multi-AZ** | DB 서버 1대가 죽으면 서비스 전체 중단 | 다른 AZ에 똑같은 예비 DB를 두고 장애 시 자동 전환 |

### 운영 (보고 알린다)

| 서비스 | 문제 | 해결 |
|---|---|---|
| **CloudWatch** | 어디가 느린지 모르면 뭘 고칠지 모름 | 계층별 지표를 한 화면에, 전/후 비교 |
| **SNS** | 알람이 콘솔에만 뜨면 아무도 못 봄 | 알람을 팀 채널(이메일·Slack)로 전송 |
| **Secrets Manager** | DB 비밀번호가 코드·설정 파일에 남음 | 비밀번호를 한 곳에 암호화 저장, 앱은 권한으로만 꺼내 씀 |

## 슬라이드 3. 헷갈리기 쉬운 것 3가지

**Q1. SSM 쓰면 NAT 게이트웨이 없어도 되나?**
아니요. 방향이 다릅니다.
- NAT = 서버가 **밖으로** 나가는 길 (패키지 설치, CloudWatch 전송)
- SSM = 사람이 서버로 **들어가는** 길 (Bastion 대신)
둘 다 필요합니다.

**Q2. NAT가 있는데 SSM은 왜?**
NAT는 들어오는 요청을 못 받습니다. 접속 수단은 Bastion 아니면 SSM 중 하나가 필요한데, SSM은 서버 1대·포트·SSH 키를 모두 없애 줍니다.

**Q3. DB도 Auto Scaling 하면 안 되나?**
DB는 데이터가 한 곳에 있어야 해서 WEB·WAS처럼 복제해 늘릴 수 없습니다. 그래서 "늘리기" 대신 "지키기"(Proxy로 연결 조절, Multi-AZ로 예비) 전략을 씁니다. 읽기 전용 복제본(Read Replica)은 앱 코드 수정이 필요해 이번 범위 밖입니다.

### 발표 때 한 문장

> "앞에서 거르고(CloudFront·WAF), 중간은 자동으로 늘리고(ASG), DB는 지킵니다(Proxy·Multi-AZ). 그리고 전부 CloudWatch로 재서 전/후를 비교합니다."
