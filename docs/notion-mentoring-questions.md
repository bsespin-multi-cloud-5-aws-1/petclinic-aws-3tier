# 멘토링 질문지 — 계층별로, "왜?"를 트레이드오프 · 비용 · 운영 부담 관점으로 (2026-09-16)

> 질문을 **1. 네트워크·진입 → 2. WEB → 3. WAS → 4. DB → 5. 전 계층 공통** 순으로 묶었다. 각 항목은 **우리 선택 → 트레이드오프 → 비용(서울 온디맨드 · 월 · 대략) → 운영 부담 → 멘토께 드릴 질문(쉬운 말)**. 용어는 ⑭ 개념 정리, 현재 구성은 ⑪ 요청 흐름.
> 월 총액 대략 **$330~380** (EC2 4대 ~$90 · NAT 2 ~$86 · ALB 2 ~$40 · RDS Multi-AZ ~$80 · Proxy ~$22 · WAF ~$11 · 로그·비밀·KMS·Backup ~$10 · CloudFront 프리 티어).

## 1. 네트워크 · 진입 (Route 53 → CloudFront → WAF → Public ALB)

### 1-1. CloudFront를 꼭 써야 하나
- **선택**: 유지. 캐시 성능보다 **경계 역할** 때문 — 공격을 엣지에서 끊고(WAF·Shield), ALB 주소를 숨기고, 전 계층이 죽어도 점검 페이지를 보여줌.
- **트레이드오프**: 빼면 구성이 단순해짐(인증서 1개, WAF를 ALB에 직접, 캐시 무효화 불필요). 대신 DDoS 흡수·오리진 은닉·점검 페이지가 약해짐. 국내 소규모면 캐시 이득 자체는 작음.
- **비용**: 프리 티어 안 → ≈ $0. **운영 부담**: 배포마다 캐시 무효화, 인증서 2개(버지니아+서울), "왜 옛 CSS가 보이지" 이슈.
- **질문**
  - ① 국내 사용자만 쓰는 작은 서비스에 CloudFront를 두는 걸 "보안 때문"이라고 설명하면 실무자 눈에 설득력이 있나요? 아니면 실무에선 그냥 ALB에 WAF를 붙이는 게 더 흔한가요?
  - ② ALB를 인터넷에서 완전히 숨기는 기능(CloudFront VPC origins)까지 넣는 건 지금 단계에서 과한가요?

### 1-2. CloudFront 캐시 설정 (무엇을 얼마나 캐시하나)
- **선택**: css·js·이미지·영상(`/static/*`·`/petclinic/resources/*`·`/images/*`)만 1일 캐시, 캐시 키는 URL 경로만. 화면(JSP)·API는 캐시 안 함.
- **트레이드오프**: 경로만 보면 Hit율은 높지만 `?v=2` 방식 캐시 버스팅이 안 통해 배포 때 무효화 명령이 필요. 동적을 안 캐시하면 안전하지만 폭주 시 WAS 부담은 그대로.
- **비용**: 무효화 월 1,000경로 무료. **운영 부담**: 정적 파일 바꿀 때마다 무효화 한 줄(9/16 Green 전환 때 실제로 겪음).
- **질문**
  - ③ 정적 파일을 바꾼 뒤 옛 파일이 보이는 문제를, 배포마다 "캐시 지우기" 명령으로 해결하는 게 실무 방식인가요, 아니면 파일 경로에 버전을 넣는(`/v2/`) 방식이 보통인가요?
  - ④ 수의사 목록 같은 **조회 API를 5~10초만 캐시**하면 폭주 때 DB 부하가 크게 줄 텐데, "몇 초 동안 옛 데이터가 보일 수 있다"는 걸 감수하고 쓰는 게 권장되나요?

### 1-3. WAF — 요청 횟수 제한(rate-based rule)
- **선택**: 한 IP가 5분에 2,000번 넘으면 차단(`rate-all`), 예약 폼(`/visits/new`)은 5분에 100번(`rate-booking`). 관리형 규칙 3종은 "이상한 요청"을, rate는 "너무 많은 요청"을 막음.
- **트레이드오프**: 숫자를 낮추면 봇은 잘 막지만 회사·학교처럼 한 IP를 여럿이 쓰는 곳은 정상 사용자가 차단될 수 있음.
- **비용**: WAF ≈ $11/월. **운영 부담**: 오탐 나면 WAF 로그에서 IP 확인 후 숫자 조정.
- **질문**
  - ⑤ 2,000번·100번은 저희가 감으로 정한 숫자인데, 실무에선 **무엇을 보고**(평소 최대 요청량? 응답 시간?) 이 숫자를 정하나요?
  - ⑥ 한 IP를 여러 사람이 같이 쓰는 경우(회사 NAT)의 오탐은 보통 어떻게 다루나요?

### 1-4. NAT Gateway 2개 · Bastion 대신 SSM
- **선택**: AZ마다 NAT 1개(총 2개), 서버 접속은 22번 포트·Bastion 없이 SSM Session Manager. (kdt5 팀 계정은 아직 Bastion 사용 중)
- **트레이드오프**: NAT 2개는 한 AZ가 죽어도 다른 AZ 서버가 인터넷(패치·AWS API)에 나갈 수 있지만 고정비가 가장 큼. SSM은 포트·키 관리가 없고 접속 기록이 남지만 팀원이 익숙하지 않음.
- **비용**: NAT ≈ $43/개·월 → 2개 $86(전체의 1/4). Bastion t3.micro ≈ $8. **운영 부담**: NAT는 없음, Bastion은 키 배포·패치·공인 IP 관리.
- **질문**
  - ⑦ 3주 실습에서 NAT를 1개로 줄여 $43 아끼고 "운영이면 AZ당 1개"라고 설명하는 게 괜찮나요, 아니면 HA를 보여주려면 2개를 유지해야 하나요?
  - ⑧ Bastion을 쓰는 팀원을 SSM으로 옮기자고 설득할 때, 실무자가 가장 납득하는 근거는 뭔가요? (22번 포트 제거? 키 유출 위험? 접속 기록?)

## 2. WEB 티어 (Public ALB → Apache ×2)

### 2-1. WEB 계층이 꼭 필요한가 · 랜딩 페이지 위치
- **선택**: Apache가 첫 화면(index.html + css·영상)을 직접 서빙하고, 앱 요청(`/petclinic/`)만 뒤의 Internal ALB → Tomcat으로 넘김(mod_proxy 리버스 프록시). mod_jk는 ALB를 못 지나서 배제.
- **트레이드오프**: WEB 계층이 있으면 정적/동적 분리·앱 서버 은닉·헤더 제어가 되지만 서버·ALB·설정이 한 벌 더 늘어남. CloudFront가 이미 정적을 캐시하므로 WEB이 정적을 서빙하는 이득은 작음.
- **비용**: t3.small ×2 ≈ $30 + Public ALB ≈ $20 → 없애면 **$50/월 절감**. **운영 부담**: Apache 설정·AMI·패치 대상 1계층 추가, 첫 화면 바뀌면 WEB 교체.
- **질문**
  - ⑨ CloudFront가 정적 파일을 다 받아주는 지금, WEB(Apache) 계층은 사실상 "앞으로 넘겨주기"만 합니다. 그래도 3-Tier로 유지하는 이유를 뭐라고 설명해야 설득력이 있나요? 아니면 "ALB → Tomcat" 2계층으로 줄여도 요구사항을 만족하나요?
  - ⑩ 첫 화면(index.html·영상 9.6MB)을 EC2가 아니라 **S3에 올리고 CloudFront가 읽게** 하면 서버 없이 되는데, 비용·운영 면에서 그게 더 낫지 않나요?

### 2-2. 부팅 스크립트(user_data) vs Golden AMI  ※ WAS도 동일
- **선택**: 지금은 서버가 켜질 때 스크립트로 Apache·CloudWatch Agent를 설치. Golden AMI(설치 완료 상태를 이미지로 저장)는 아직 안 만듦.
- **트레이드오프**: 스크립트 방식은 AMI 관리가 없지만 부팅이 느리고(WEB 1분·WAS 8분) 외부 저장소가 죽으면 부팅 실패. Golden AMI는 1~2분에 뜨지만 패치마다 이미지를 다시 구워야 함.
- **비용**: AMI ≈ $1/월. **운영 부담**: 수동 `create-image` v1/v2, 자동화하려면 EC2 Image Builder 파이프라인.
- **질문**
  - ⑪ 3주 프로젝트에서 AMI 자동 생성(Image Builder)까지 만들 가치가 있나요, 아니면 손으로 AMI v1·v2를 만드는 걸로 충분한가요?

## 3. WAS 티어 (Internal ALB → Tomcat ×2)

### 3-1. 자동 증설(ASG) — 언제 늘릴지 정하는 기준
- **선택**: 지금 mc-deploy는 고정 2대. 설계는 ASG 2~8대, CPU 60% + "한 대당 1분 300요청" 넘으면 증설, 이벤트 15분 전 4대로 예약 증설, 축소 때 로그를 S3에 저장 후 종료.
- **트레이드오프**: CPU 기준은 단순하지만 Java 앱은 CPU가 늦게 오름. 요청 수 기준은 빠르지만 "300"의 근거가 필요. 예약 증설은 확실하지만 시간을 미리 알아야 함.
- **비용**: ASG 자체 무료, 최대 8대면 ≈ $240/월 상한. **운영 부담**: AMI 교체·인스턴스 새로 고침 절차, 새 서버가 뜨는 8분(부팅 빌드) 동안은 대응 불가.
- **질문**
  - ⑫ WAS를 늘리는 기준으로 **CPU**와 **한 대당 요청 수** 중 뭘 1순위로 두나요? "한 대당 300요청"이라는 숫자는 부하 테스트로 "한 대가 버티는 한계의 70~80%"로 잡는 게 맞나요?
  - ⑬ 새 서버가 요청을 받기까지 8분이면 폭주를 감지하고 늘려도 이미 늦습니다. 이럴 땐 **시간표로 미리 늘리는(예약 증설)** 게 현실적인 답인가요, 아니면 Golden AMI로 1~2분으로 줄이는 게 먼저인가요?

### 3-2. 앱 배포 방식 — WAR에 DB 정보가 박히는 문제
- **선택**: 서버가 켜질 때 Secrets Manager에서 DB 비밀번호를 받아 **빌드하면서 WAR 안에 써넣음**(이 앱 구조상 실행 시 주입이 안 됨).
- **트레이드오프**: 소스 수정 0줄이지만, WAR가 "그 환경 전용"이 되고 비밀번호가 WAR 안에 들어가 AMI에 넣을 수 없음. 해결책 **JNDI**(Tomcat 설정 파일에 DB 정보를 두고 앱은 이름만 참조 — 이 앱에 이미 준비된 프로필이라 코드 수정 없이 가능).
- **비용**: 없음. **운영 부담**: JNDI로 바꾸면 부팅 시 설정 파일 한 개만 쓰면 되고 AMI에 WAR를 넣을 수 있음.
- **질문**
  - ⑭ 옛날식 Spring(XML 설정) 앱에서 DB 접속 정보를 WAR 밖으로 빼는 실무 표준은 JNDI인가요? 환경변수나 Parameter Store 조회 방식과 비교해 뭘 추천하시나요?

### 3-3. 세션 저장소(Redis)와 큐(SQS)가 필요한가
- **선택**: 둘 다 안 씀. 로그인이 없어 서버 간에 공유할 "사용자 상태"가 없고, 비동기 작업도 없음. 넣으려면 앱 코드를 고쳐야 함.
- **트레이드오프**: 없으면 단순·저렴. 로그인이나 예약 폭주 완충이 필요해지면 그때 코드 변경. Redis는 노드 상시 비용, SQS는 쓴 만큼.
- **비용**: ElastiCache 최소 ≈ $12/노드(HA면 2개), SQS 백만 건 $0.40. **운영 부담**: Redis는 패치·failover·메모리 관리, SQS는 처리 코드 운영.
- **질문**
  - ⑮ 로그인이 없는 앱에서 "세션 유지" 요구사항은 어떻게 해석해야 하나요? ALB가 같은 사용자를 같은 서버로 보내는 기능(스티키)으로 충분한가요?
  - ⑯ 예약 폭주 때 요청을 **큐(SQS)에 줄 세워** DB를 보호하는 설계와, 지금처럼 **Proxy 커넥션 풀 + 서버 증설로 버티는** 설계 중 — 코드 변경을 감수할 만큼 SQS 이득이 큰가요?

### 3-4. 새 버전 배포 방식 (Blue/Green)
- **선택**: 지금은 **롤링**(AZ-a 서버 교체 → 확인 → AZ-c 교체). 별도 Green 서버 묶음을 띄우고 트래픽을 10→50→100%로 옮기는 **가중치 전환**은 아직 안 함.
- **트레이드오프**: 롤링은 서버가 늘지 않고 단순하지만 되돌리려면 다시 교체해야 함. 가중치 전환은 문제 시 0%로 즉시 롤백되고 발표에 보기 좋지만 서버가 2배·설정이 복잡.
- **비용**: 가중치 전환 중엔 WAS 4대 ≈ +$60(전환 시간만큼). **운영 부담**: 대상 그룹 2개·리스너 규칙 관리.
- **질문**
  - ⑰ 발표에서 "Blue/Green 전환"을 보여주려면 Green 서버 묶음 + 가중치 방식이 필요한가요, 아니면 AZ별 롤링 교체도 Blue/Green으로 인정되나요?

## 4. DB 티어 (RDS Proxy → RDS MySQL Multi-AZ)

### 4-1. DB 비밀번호 관리 · 자동 교체
- **선택**: RDS가 만든 admin 비밀번호는 **7일마다 자동으로 바뀜**(끌 수 없음). WAS는 빌드 때의 비밀번호를 WAR에 갖고 있어 바뀌면 접속 실패 → 앱 전용 계정(`petclinic_app`)을 만들고 그 비밀번호는 **바꾸지 않기로** 함. DB 구간은 TLS 강제.
- **트레이드오프**: 안 바꾸면 운영이 단순하지만 유출 시 사람이 바꿔야 함. 바꾸려면 매번 WAS 재빌드·재기동(빌드 주입 구조의 한계). IAM 토큰 인증은 이 문제가 없지만 앱 코드 필요.
- **비용**: 비밀 ≈ $1/월. Secrets Manager·SSM 전용 사설 통로(VPC 엔드포인트) 추가 시 ≈ $8/월. **운영 부담**: 앱 비밀 수동 교체 절차 문서화.
- **질문**
  - ⑱ 앱이 쓰는 DB 비밀번호를 "자동 교체 안 함"으로 두는 게 보안 관점에서 허용되는 수준인가요? 교체를 꼭 해야 한다면, WAR에 비밀번호가 박히는 구조에서 권장하는 방법은 뭔가요(재빌드 / JNDI 설정 파일 갱신 / IAM 토큰)?
  - ⑲ 서버가 Secrets Manager·SSM에 갈 때 인터넷(NAT)을 거치지 않도록 **VPC 엔드포인트**($8/월)를 두는 게 작은 서비스에서도 표준인가요?

### 4-2. RDS Multi-AZ를 켜 둘 가치
- **선택**: Multi-AZ(다른 AZ에 대기 복제본, 장애 시 1~2분 자동 전환, 데이터 손실 0) 켜 둠.
- **트레이드오프**: 요구사항 "무손실(RPO 0)"을 증명하지만 비용이 2배(≈ $40 → $80).
- **질문**
  - ⑳ 실습 3주 동안 Multi-AZ를 계속 켜 둘 가치가 있나요, 아니면 평소엔 끄고 발표·failover 시연 때만 켜는 게 현실적인가요?

### 4-3. 개인정보 보관·파기 · 진료 파일 저장
- **선택**: 개인정보(보호자 이름·전화·예약)는 RDS 행으로만 존재 → 백업 7일·시점 복구·삭제 방지·암호화로 보호. 진료 **파일**(X-ray 등) S3 저장은 시나리오에서 뺌. 보관 기간 규칙(lifecycle)은 로그·감사 로그에만.
- **트레이드오프**: 파일 저장을 빼면 단순하지만 "의료 데이터 보호"라는 발표 축이 약해짐. DB 안의 개인정보는 S3처럼 자동 만료 규칙이 없어 정책 문서 + 주기적 삭제 작업으로 증명해야 함.
- **비용**: RDS 백업은 DB 크기까지 무료, Backup 볼트 $0.095/GB. **운영 부담**: 보존 기간·파기 정책 문서, 복구 리허설.
- **질문**
  - ㉑ 개인정보가 DB 행으로만 있을 때 "보존 기간이 지나면 파기한다"를 어떻게 증명하나요? 프로젝트 수준에선 정책 문서만으로 충분한가요, 아니면 삭제 작업(예약 SQL)까지 만들어야 하나요?
  - ㉒ 발표 평가를 생각하면 진료 파일 S3 저장(Object Lock·Macie)을 다시 넣는 게 유리한가요, 지금처럼 범위를 줄인 게 맞나요?

## 5. 전 계층 공통 (로그 · 권한 · 이름)

### 5-1. 로그 수집 범위
- **선택**: 5종 — 앱 로그(Apache·Tomcat), ALB 접속 로그, WAF 로그, SSM 접속 기록, CloudTrail(누가 AWS에서 뭘 했나). VPC Flow Logs·RDS 느린 쿼리 로그·S3 데이터 이벤트는 제외.
- **트레이드오프**: 많이 모을수록 사고 조사에 좋지만 비용·노이즈 증가.
- **비용**: CloudWatch Logs 수집 $0.76/GB, CloudTrail 첫 추적 무료, Flow Logs 켜면 $0.5/GB 이상. **운영 부담**: 보관 기간·암호화·조회 도구 숙련.
- **질문**
  - ㉓ 필수 로그로 이 5종이면 적절한가요? 멘토님 경험상 장애 났을 때 **가장 먼저 여는 로그**는 뭔가요?
  - ㉔ Phase 3(폭주 테스트)에서 DB 병목을 찾으려면 **느린 쿼리 로그**를 켜는 게 비용 대비 값어치가 있나요?

### 5-2. 권한 — 기본 거부 + 태그로 허용(ABAC)
- **선택**: 역할마다 필요한 자원만 허용. 모든 자원에 `Project=petclinic-3tier` 등 태그를 붙이고 "이 태그가 붙은 것만 만질 수 있다"는 정책 초안.
- **트레이드오프**: 태그 기반은 정책이 짧고 자원이 늘어도 안 고치지만, 태그를 안 붙이면 접근이 막히고 태그를 바꿔치기하면 뚫려서 태그 변경 권한도 막아야 함.
- **비용**: 없음. **운영 부담**: 태그 표준 강제(Terraform은 자동, 콘솔로 만든 건 수동), 정책 시뮬레이터로 테스트.
- **질문**
  - ㉕ 조직 단위 정책(SCP)이 없는 팀 계정에서, IAM 사용자 정책만으로 태그 기반 권한을 강제하는 **현실적인 최소 구성**은 뭔가요?
  - ㉖ 태그를 바꿔서 권한을 우회하는 걸 막으려면 태그 변경 권한을 어떻게 제한하는 게 관례인가요?

### 5-3. 이름 규칙
- **선택**: `mc-<계층>-<구분>-<AZ>`(예 `mc-was-c`, `mc-sg-rds`), 버킷은 계정 ID 접미, 로그 그룹 `/mc/<계층>/<종류>`. 환경(lab/prod)은 태그로. kdt5 팀이 콘솔로 만든 `test-*` 이름은 규칙 밖.
- **트레이드오프**: 이름에 환경·계정까지 넣으면 한눈에 보이지만 길이 제한(ALB 32자)에 걸림. ALB·대상 그룹은 이름 변경이 불가라 규칙에 맞추려면 지웠다 다시 만들어야 함.
- **질문**
  - ㉗ 환경(lab/prod)이나 계정을 **이름에 넣나요, 태그로만 두나요**? 실무 관례가 궁금합니다.
  - ㉘ 이름을 못 바꾸는 자원(ALB·대상 그룹·RDS)이 규칙에 안 맞을 때, 지우고 다시 만드는 게 정답인가요, 태그로 표시하고 그냥 두나요?
