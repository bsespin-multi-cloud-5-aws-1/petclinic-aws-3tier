# 멘토링 질문지 — "왜?"를 트레이드오프 · 비용 · 운영 부담 관점으로 (2026-09-16)

> 각 항목: **우리 선택 → 트레이드오프 → 비용(서울 온디맨드 · 월 · 데이터 전송 제외 · 대략) → 운영 부담 → 멘토께 드릴 질문**.
> 현재 mc-deploy As-Built 기준(`docs/architecture-mc-deploy-asbuilt.png`). 월 총액 대략 **$330~380** (EC2 4대 ~$90 · NAT 2 ~$86 · ALB 2 ~$40 · RDS Multi-AZ ~$80 · Proxy ~$22 · WAF ~$11 · 로그·비밀·KMS·Backup ~$10 · CloudFront 프리 티어).

## 1. CloudFront 캐시 키 · WAF rate-based rule
- **선택**: 정적 Behavior(`/static/*`·`/petclinic/resources/*`·`/images/*`)만 캐시, 키 = 경로만, TTL 1일. 동적 `*`는 캐시 없음. WAF rate-all 2,000/5분·rate-booking 100/5분.
- **트레이드오프**: 키를 좁히면 Hit율↑ 대신 `?v=` 캐시 버스팅 불가(무효화 필요). 동적을 안 캐시하면 안전하지만 폭주 시 ALB·WAS 부담은 그대로. rate 상한을 낮추면 봇은 막지만 회사 NAT 뒤 다수 사용자 오탐.
- **비용**: CloudFront 1TB/월·1천만 요청 프리 티어 → 사실상 $0. 무효화 월 1,000경로 무료. WAF $5/ACL + $1/규칙×5 + $0.60/백만 요청 ≈ **$11**.
- **운영 부담**: 정적 파일 배포마다 무효화 한 줄. rate 오탐 시 WAF 로그로 IP 확인·상향.
- **질문**: ① 소규모 국내 서비스에서 rate 2,000/5분·예약 100/5분이 합리적인 출발점인가, 어떤 지표로 튜닝하나? ② 읽기 API(`/vets.json`)에 5~10초 짧은 TTL 캐시를 두는 건 권장인가, 정합성 문제는? ③ 캐시 버스팅을 무효화로 하는 것과 경로 버전(`/v2/`)으로 하는 것 중 운영상 무엇이 낫나?

## 2. WEB(Apache) index.html 유지 · mod_proxy 리버스 프록시
- **선택**: 랜딩(index.html·정적)은 Apache 직접, 앱 `/petclinic/`만 mod_proxy_http → Internal ALB. mod_jk 배제(ALB 통과 불가).
- **트레이드오프**: WEB 계층을 두면 정적/동적 분리·앱 서버 은닉·헤더 제어를 얻지만 홉·인스턴스·설정이 하나 더. CloudFront가 이미 정적을 캐시하므로 WEB의 정적 서빙 가치는 작음.
- **비용**: t3.small ×2 ≈ **$30** + WEB용 ALB ≈ $20. 없애면 절감.
- **운영 부담**: Apache 설정·AMI·패치 대상 1계층 추가. 랜딩 내용이 바뀌면 WEB 교체.
- **질문**: ① CloudFront + Internal 없이 "Public ALB → Tomcat" 2계층으로 줄여도 요구사항(3-Tier·보안)을 충족하는가, WEB 계층의 존재 이유를 무엇으로 설명해야 설득력 있나? ② 정적 랜딩을 WEB EC2가 아니라 S3+CloudFront로 옮기는 게 비용·운영상 더 낫지 않나?

## 3. 세션 저장소(Redis) · 큐(SQS)
- **선택**: 둘 다 미도입. 로그인·비동기 작업이 없고, 도입 시 앱 코드 변경 필요(소스 0줄 원칙).
- **트레이드오프**: 없으면 단순·저렴하지만 로그인/예약 폭주 완충이 생기면 뒤늦게 코드 변경. ElastiCache는 노드 상시 비용, SQS는 사용량 과금.
- **비용**: ElastiCache cache.t4g.micro ≈ **$12/노드**(HA면 ×2), SQS 백만 요청 $0.40.
- **운영 부담**: Redis는 패치·failover·메모리 관리 추가, SQS는 거의 없음(단 consumer 코드 운영).
- **질문**: ① 로그인이 없는 PetClinic에서 "세션 유지" 요구를 어떻게 해석해야 하나(ALB 스티키로 충분?) ② 예약 폭주 시나리오에서 SQS 완충 vs RDS Proxy+ASG 흡수 — 코드 변경을 감수할 만큼 SQS 이득이 큰가?

## 4. CloudWatch Agent — init script vs Golden AMI
- **선택**: 지금은 user_data가 설치+SSM 파라미터로 설정(부팅 +30초). Golden AMI로 가면 설치는 굽는 단계.
- **트레이드오프**: 부트스트랩은 AMI 관리가 없지만 부팅 8분(WAS)·외부 저장소 의존·ASG 증설 지연. Golden AMI는 증설 1~2분이지만 AMI 파이프라인·버전 관리·계정별 재생성 필요.
- **비용**: AMI 스냅샷 $0.05/GB ≈ $1/AMI. 부트스트랩은 NAT 전송비 소폭.
- **운영 부담**: Golden AMI는 패치마다 재생성(EC2 Image Builder면 자동화 가능).
- **질문**: ① 3주 프로젝트에서 EC2 Image Builder 파이프라인까지 구성할 가치가 있나, 수동 `create-image` v1/v2로 충분한가? ② WAR에 DB 접속정보가 빌드 시 박히는 구조에서 AMI를 환경 독립적으로 만드는 표준 방법(JNDI·환경변수·Parameter Store 중)은?

## 5. CloudTrail · CloudWatch Logs 수집 범위
- **선택**: 로그 5종(앱·ALB·WAF·SSM·CloudTrail). VPC Flow Logs·RDS 로그(일반/느린 쿼리)·S3 데이터 이벤트는 제외.
- **트레이드오프**: 많이 모을수록 사고 조사에 좋지만 수집·보관 비용과 노이즈↑. 
- **비용**: CloudWatch Logs 수집 $0.76/GB + 보관 $0.03/GB·월, CloudTrail 첫 관리 이벤트 추적 무료(S3 저장만), Flow Logs 추가 시 $0.5/GB 이상.
- **운영 부담**: 보관 기간·KMS·버킷 정책 관리, 조회 도구(Logs Insights/Athena) 숙련.
- **질문**: ① "필수 로그" 최소 세트로 5종이 적절한가, 멘토님 경험상 사고 때 가장 먼저 찾는 로그는? ② RDS slow query log를 켜서 Phase 3 병목 분석에 쓰는 게 낫지 않나(비용 대비)?

## 6. ASG Target Tracking · 증설 시 로그
- **선택**: mc-deploy는 EC2 고정 2대(코드 단순화), 설계는 ASG(WEB CPU 60% 2~6 · WAS CPU 60%+요청 300/대 2~8 · 예약 증설). 종료 훅 300s로 로그 S3 sync.
- **트레이드오프**: 목표 추적은 단순하지만 CPU 지표는 JVM 워크로드에서 늦게 반응, 요청 수 기준은 빠르지만 임계값 산정 필요. 예약 증설은 확실하지만 시간 예측 필요.
- **비용**: ASG 자체 무료. 최대 8대 t3.medium ≈ $240/월 상한. 워밍업 동안 이중 과금.
- **운영 부담**: LT 버전·AMI 교체·인스턴스 새로 고침 절차, 훅 실패 시 종료 지연.
- **질문**: ① WAS 증설 지표로 CPU vs ALBRequestCountPerTarget 중 무엇을 1순위로 두는 게 맞나, 300/대의 근거를 어떻게 잡나? ② 워밍업 300s(부트스트랩 8분)면 폭주 대응이 늦는데, 예약 증설로 보완하는 게 현실적인 답인가?

## 7. Secrets Manager — 비밀 취급 · 교체
- **선택**: RDS 관리형 admin 비밀(7일 자동 교체) + **앱 전용 사용자 비밀(교체 없음)** 으로 분리, WAS는 빌드 시 주입, Proxy가 SECRETS 인증. TLS 3중(Proxy require_tls·파라미터·JDBC).
- **트레이드오프**: 앱 비밀을 교체 안 하면 운영 단순하지만 유출 시 무효화가 수동. 교체하면 WAS 재빌드/재기동 필요(빌드 시 주입 구조의 한계). IAM 인증(토큰)은 교체 문제를 없애지만 앱 코드 필요.
- **비용**: 비밀 $0.40/개·월 + API 호출 $0.05/만 건 ≈ **$1**. Secrets Manager VPC 엔드포인트 추가 시 ≈ $8/월(NAT 전송비 대체).
- **운영 부담**: 앱 비밀 수동 교체 절차(비밀 갱신 → WAS 롤링) 문서화 필요.
- **질문**: ① 앱 DB 비밀을 "교체 없음"으로 두는 게 허용되는 수준인가, 교체한다면 빌드 시 주입 구조에서 권장 패턴은? ② Secrets Manager·SSM용 VPC 엔드포인트를 두는 것이 NAT 경유보다 보안·비용에서 표준인가?

## 8. 스토리지 · Lifecycle (진료 기록 · 개인정보)
- **선택**: 앱 기능 추가 없음. 개인정보=RDS(백업 7일·PITR·Backup 볼트·삭제 방지·암호화). 진료 파일 S3는 시나리오 제외. lifecycle은 로그·감사에만.
- **트레이드오프**: 파일 저장을 빼면 Object Lock·Macie·데이터 이벤트 등 큰 축이 사라져 단순하지만 "의료 데이터 보호" 발표 축이 약해짐.
- **비용**: RDS 백업 보관은 DB 크기까지 무료, Backup 볼트 $0.095/GB, S3 lifecycle 전환 $0.01/천 객체.
- **운영 부담**: 보존기간·파기 정책 문서, 복구 리허설(PITR·failover 드릴).
- **질문**: ① 개인정보 보존·파기를 RDS 행 수준에서 어떻게 증명하나(요구사항이 "정책 문서"로 충분한가)? ② 발표 관점에서 진료 파일 S3 저장을 다시 넣는 게 평가에 유리한가, 범위 유지가 맞나?

## 9. 권한 — 기본 거부 + 명시적 허용 · 태그 기반(ABAC)
- **선택**: 역할별 ARN 단위 허용, default_tags(Project·Tier…) 로 ABAC 조건, 태그 없는 생성 거부 정책 초안.
- **트레이드오프**: ABAC는 정책 수가 줄고 확장에 강하지만 태그 누락 한 번에 접근이 막히고 태그 자체를 보호해야 함(`aws:TagKeys` 조건). RBAC(역할별 정책)은 이해 쉬움.
- **비용**: 없음. 
- **운영 부담**: 태그 표준 강제(Terraform은 자동, 콘솔 구축본은 수동), 정책 테스트(IAM Policy Simulator).
- **질문**: ① 팀 계정(kdt5)에서 SCP 없이 IAM 사용자 정책만으로 ABAC를 강제하는 현실적인 최소 세트는? ② 태그 변경 권한 자체를 어떻게 제한하는 게 관례인가?

## 10. 네이밍 규칙
- **선택**: `mc-<tier>-<구분>[-<az>]`, 버킷은 계정 ID 접미, 로그 그룹 `/mc/<tier>/<stream>`, 태그 6종. kdt5 콘솔 구축본(`test-*`)은 규칙 밖.
- **트레이드오프**: 짧은 접두사는 편하지만 계정·환경 구분이 약함(`mc-prod-…` 같은 env 세그먼트 추가 시 이름 길이 제한(ALB 32자·SG 255자) 주의).
- **운영 부담**: 콘솔 리소스 개명(재생성 필요한 것 있음: ALB·TG 이름 변경 불가).
- **질문**: ① 환경(lab/prod)·계정을 이름에 넣을지 태그로만 둘지, 실무 관례는? ② 이름 변경이 불가능한 리소스(ALB·TG·RDS 식별자)는 재생성이 정답인가, 태그로 덮고 가나?

## 11. CDN(CloudFront)을 정말 써야 하나
- **선택**: 유지. 이유는 성능보다 경계(WAF/Shield 엣지 차단·오리진 은닉·5xx 점검 페이지·엣지 TLS).
- **트레이드오프**: 없애면 구성 단순(ACM 1개·WAF REGIONAL·홉 하나↓·캐시 무효화 불필요)하지만 DDoS 흡수·오리진 은닉·전 계층 장애 안내가 약해짐. 국내 소규모면 캐시 이득 자체는 작음.
- **비용**: 프리 티어 안 → ≈ $0. 없애도 WAF REGIONAL 비용은 동일.
- **운영 부담**: 배포마다 무효화, 두 리전 인증서, 캐시 때문에 "왜 옛 CSS가 보이지" 류 이슈.
- **질문**: ① 국내 단일 리전·소규모 서비스에서 CloudFront를 "보안 경계"로 정당화하는 것이 실무적으로 설득력 있나, 아니면 ALB+WAF REGIONAL이 더 흔한 선택인가? ② CloudFront VPC origins(ALB internal화)까지 가는 게 지금 단계에서 과한가?

## 추가 (이전 라운드에서 남은 판단)
- **Blue/Green 단위**: 지금은 인스턴스 교체(Rolling, AZ별). 별도 Green TG + 가중치 전환이 발표에 더 좋은가 vs 운영 복잡도?
- **RDS Multi-AZ**: 실습 3주에 Multi-AZ(비용 2배)를 켜둘 가치 — RPO 0 요구 증명 vs 비용?
- **NAT 2개**: AZ당 NAT($86/월)가 가장 큰 고정비 중 하나 — 실습에선 1개로 줄여도 되나, HA 요구와의 균형?
- **Bastion 제거·SSM**: kdt5 팀은 Bastion을 쓰고 있음 — SSM 전환을 강제할 근거를 어떻게 설명하나?
